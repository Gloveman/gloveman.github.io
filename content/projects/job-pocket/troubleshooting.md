## 🛠 문제 상황 (Problem)
자소서 초안 품질 미달 시 최대 3회까지 재생성을 시도하는 루프 과정에서 다음과 같은 비효율이 발생했습니다.
- 동일한 쿼리임에도 불구하고 매 시도마다 **자소서 DB 검색(Retrieval)**과 **샘플 분석(LLM Analysis)**이 반복됨.
- 이로 인해 API 호출 비용이 3배로 증가하고, 사용자 응답 지연 시간이 크게 늘어남.

## 🔍 원인 분석 (Root Causes)
생성 로직(`build_draft`) 내부에 검색과 분석 단계가 강결합되어 있어, 단순히 생성을 다시 하기 위해 전체 파이프라인을 다시 실행하는 구조였습니다.

## 💡 해결 방법 (Solution)
1. **로직 분리 (Hoisting)**: 샘플 검색 및 분석 단계를 재생성 루프 외부로 이동시켜 최초 1회만 수행하도록 변경.
2. **컨텍스트 재사용**: 추출된 샘플 데이터를 변수에 저장하고, 루프 내부의 생성 단계(`build_draft_with_exaone`)에서는 이 데이터를 그대로 주입받아 사용.

## ✅ 결과 및 수치
- **응답 속도 개선**: 재생성 시 소요 시간이 기존 대비 약 **60% 단축**.
- **비용 절감**: 불필요한 LLM 분석 호출을 제거하여 API 비용 효율성 극대화.
- **교훈**: 파이프라인 설계 시 **멱등성(Idempotency)**이 보장되는 단계와 반복이 필요한 단계를 명확히 분리하는 것이 성능 최적화의 핵심임을 배웠습니다.
